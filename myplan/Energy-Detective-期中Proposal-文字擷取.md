## Abstract 摘要

本專案規劃以真實家庭用電紀錄結合 AI Agent、Domain Knowledge 與 Data Analytics，將用電資訊轉為有依據的分析與建議。以下依研究動機、挑戰、解法、方法、評估與預期成果說明提案。

### Attention Getter Motivation

住宅能源管理具有實際需求。IEA 在 2025 年報告指出，住宅約占建築能源需求的 70%[1]；近期實地研究也關注，讓住戶了解自己的用電情況，是否有助於調整用電習慣與減少能源消耗[2][3]。因此，本專案希望將家庭用電紀錄轉為容易理解、能夠查核的分析結果，協助使用者掌握用電情況並判斷改善方向。

### But Challenge

既有能源 Agent 能整合自然語言與工具，但研究仍觀察到分析錯誤、未遵守使用限制，以及說明與執行結果不一致等問題 [4][5]。資料的時間與設備粒度，以及缺值情況，也會限制原因判斷；僅憑回答流暢，無法確認建議是否有足夠依據。

### Cure Proposed Solution

本專案提出 Energy Detective，一個以回答可靠性與證據可追溯性為主要特色的家庭用電分析與節能決策 Agent，支援查詢、比較、異常候選分析、短期預測與有依據的檢查建議。

### Development Method

系統規劃以 UCI 單一家庭的歷史紀錄進行小時級用電分析 [7]。由一個透過 Cloud API 使用的 LLM Agent 理解問題、選用事先建立的分析工具，再根據工具結果整理回答。分析方法結合 Random Forest、MAD 規則與附有來源的能源知識，並透過證據紀錄與回答檢查，核對數字、圖表及限制說明，最後以 Streamlit 呈現。

### Experiments Evaluation Plan

預測資料依時間順序切分為 70% 訓練、15% 驗證與 15% 測試，使用 MAE 與 RMSE，比較候選模型、上一小時及前一天同時段兩個基準方法。Agent 先以 10 題進行試測，再用 50 題正式任務比較有／無外部回答檢查與修正的兩個條件；每個條件每題執行 3 次，評估任務完成率、數值與證據一致性、限制處理及執行成本。

### Findings Expected Outcomes

預期產出可實作的 Agent 設計、可追溯的回答紀錄及分層評估方案，並檢驗回答檢查機制的效果與額外成本。Proposal 階段尚未執行實驗，因此尚無可靠性改善幅度或實測節電結果。

## Introduction 緒論

### Attention Getter 研究重要性與證據

住宅能源管理是能源效率的重要議題。IEA 在《Energy Efficiency 2025》中指出，住宅約占全球建築能源需求的 70%，且不同地區的氣候、設備與能源用途具有差異 [1]。這說明改善家庭能源管理具有研究價值，但也意味著建議需要依具體情境形成，不能將宏觀能源統計直接套用到單一家庭。

向住戶提供用電資訊的研究也提供了研究動機。Boomsma 等人在荷蘭家庭的隨機對照實驗中，觀察到提供即時能源資訊後，電力使用量有所下降 [2]；Paunov 等人的學生住宅研究則顯示，社會比較與能力提升提示均可能影響用電行為，但效果受研究情境與使用者差異限制 [3]。因此，本專案希望進一步探討如何提供可理解的資訊與建議；是否真的節電，仍須另外進行介入與行為追蹤。

### Background 應用與技術背景

本專案的服務對象是希望理解家庭用電的一般使用者，支援查詢、比較、異常候選分析、短期預測與建議五類情境。以「昨天比前一天多用了多少電？應該先檢查哪個時段？」為例，系統需先確認日期與資料區間，計算總用電量及各設備群的用電差異，再結合能源知識解釋結果。

近期能源 Agent 已整合自然語言、分析工具與設備資訊 [4]，亦有研究將自然語言需求轉為家庭設備排程 [5]。本專案延續工具協調與資料分析的方向，現階段以公開歷史紀錄驗證設計，不納入實體感測器串接或家電控制。

### Problem 本專案要解決的問題

本專案聚焦於：如何讓家庭用電 Agent 的回答在數字、時間與單位上正確，讓分析與建議能追溯到實際資料，並在資訊不足時適當說明限制？

這個問題包含三種情況。第一，回答即使流暢，也可能用錯日期、誤將功率當成電量，或引用不相符的計算結果。第二，偏高的用電只是相對歷史基準的觀察，不能直接斷言為浪費、設備故障或特定行為。第三，預測是依歷史資料形成的估計，不是已經發生的事實。

### Existing Limitations 相關工作與資料限制

既有研究已評估能源 Agent 的回答與工具能力，但不同任務仍有錯誤，且生成式分析的穩定性受到關注 [4]。排程研究亦顯示，模型說明與實際執行結果需要分別檢查 [5]。另一方面，負載預測研究提供預測方法及誤差比較 [6]，卻不能單靠預測表現判定對話中的建議是否有證據支持。

本專案採用 UCI 的單一家庭歷史資料 [7]。其中部分紀錄是多種設備共用電表的量測數據，無法辨識個別電器的用電情況，也缺乏真實異常成因與採取建議後的追蹤紀錄。因此，系統僅提供資料能支持的分析與檢查方向，不宣稱能確認單一電器故障、代表台灣家庭，或證明實際節電成效。

### Innovation 本專案的設計特色

本專案提出 Energy Detective，以回答可靠性與證據可追溯性為主要設計特色。Agent 預計依使用者需求選擇資料查詢、比較、異常分析與預測工具，再結合能源知識形成回答。計算結果由工具產生，回覆前檢查其時間範圍、單位與引用內容，並區分直接觀察、預測與原因假設。

使用者提出超出資料能力的問題時，系統預計透過澄清、限制說明或縮小結論範圍處理。例如，資料只能顯示某個設備群的用電增加時，回答應指出優先檢查的設備群與時段，並詢問相關資訊，避免直接認定某台電器是原因。

這是本專案選定的整合與驗證方向，不主張上述設計元素皆為首次提出。其實際有效性將由後續對照測試檢驗。

### Contributions 預期貢獻與研究問題

本專案預期產出：

具領域知識的分析 Agent 設計：整合五類家庭用電任務，明確描述需求、工具、能源知識與回答的關係。

可核對的回答依據：規劃記錄分析區間、資料涵蓋情況、計算方法與工具結果，使數字和建議具有可追溯依據。

分層評估計畫：分別評估預測誤差、分析任務正確性及證據一致性，並納入資料不足與模糊需求案例。

## Related Work 相關研究

### 能源領域與 AI 技術研究

IEA 的 2025 年報告將住宅能源效率列為重要課題；其中住宅約占建築能源需求的 70% [1]。這項統計涵蓋各類能源，不是家庭電力占比。對本專案而言，能源背景用來說明研究重要性，不能據此推導 Agent 能達成的節電幅度。

Boomsma 等人的隨機對照研究追蹤荷蘭家庭，透過即時能源顯示器向住戶呈現能源使用資訊，報告電力使用減少 2.2%、天然氣使用減少 6.9% [2]。Paunov 等人則比較社會比較資訊與能力提升提示，在學生住宅情境中發現兩種策略相對控制組的用電趨勢均有改善，但兩者差異未達統計顯著 [3]。這些研究支持進一步探討資訊與建議的作用，也提醒我們：提供回答、使用者採取行動與實際節電，需要分別驗證。

He 與 Jazizadeh 已提出具情境感知能力的能源管理 Agent，整合資料分析、設備互動與多面向評估 [4]。Jonah 等人的新版研究則以工具調用 Agent 執行多設備排程，指出自然語言解釋與實際動作必須分別檢查 [5]。因此，本專案的定位不能只是將 LLM 接上能源資料，也不能聲稱既有能源 Agent 完全沒有可靠性評估。

在預測方法上，Muqtadir 等人以 boosting 集成分析下一小時住宅負載，顯示方法表現會隨站點而變 [6]。本專案採不同的單一家庭資料，須重新建立基準與時間序列測試，不能沿用其數值作為本系統成效。

## Deep Research 深入領域研究

本章以家庭用電分析與能源管理 Agent 為範圍。五項思維依量測與研究證據整理；三項爭論選取與本專案設計最相關的取捨，不宣稱其爭議程度有全領域排名。

### 五個核心思維模式

#### M1 先定義量測項目與目標，再判斷改善

意義：功率 kW 是某時段的耗電速率；電量 kWh 是功率在時間上的累積。降低電量、降低尖峰、降低費用及降低排放是不同目標，必須各自有對應資料與計算方法。

證據：UCI 說明，全屋用電功率以每分鐘平均值記錄，單位為 kW；設備群用電量則以每分鐘的電量記錄，單位為 Wh [7]。IEA 將需求彈性描述為調整用電時點或數量，以改善系統運作 [8]。依量測定義，將每筆分鐘平均功率乘以 1/60 小時後加總，即可取得 kWh；設備群每分鐘的 Wh 電量加總後，則需除以 1000 換算為 kWh。

如何影響設計：查詢先確定目標、單位與期間；功率與電量由不同的計算規則處理。沒有費率或碳強度資料時，不輸出確定的省費／減碳數字。若需要假設情境，必須標為假設，不能混入實際量測結果。

#### M2 分析能力受資料涵蓋範圍與粒度限制

意義：量測內容、缺失情況，以及時間與設備的記錄粒度，決定系統能回答的範圍。缺值不等於零；同一筆設備群用電紀錄可能包含多台電器，無法直接辨識各電器的個別耗電量。

證據：UCI 資料存在缺值，各組設備群用電紀錄也可能涵蓋多種設備 [7]。短期負載研究亦先進行缺值、異常與資料完整性處理 [6]。

如何影響設計：計算前檢查有效資料涵蓋率、單位與重複紀錄，並區分觀測值與補值。不完整時段不能直接視為完整總量；缺乏個別電器資料時，回答僅描述相關區域或設備群的變化，並列出需要補查的資訊。初版不自動補值；每小時 60 個不同分鐘均有有效紀錄時，才產生完整小時電量，詳見 Data 與分析方法。

#### M3 異常是需要解釋的線索，原因要另有證據

意義：異常取決於比較基準與使用情境。用電偏高可能源於正常活動、季節變化或量測問題；統計偏離不能單獨證明浪費、故障或因果關係。

證據：UCI 沒有提供真實故障、浪費或個別電器的成因標籤 [7]；住宅預測研究顯示站點特性與資料品質影響結果 [6]；能源 Agent 需取得環境與設備情境，才能提供具體支援 [4]。因此，僅憑設備群的用電變化，無法確認造成變化的原因；這是本專案依資料結構作出的判斷。

如何影響設計：異常結果附上參考時段與比較方法；區分「觀察到的變化」「可能解釋」「需補證據」。使用者詢問原因時，Agent 可追問活動或設備資訊；不將所有高值自動刪除，也不把高值一律當成浪費。

#### M4 預測須依當時可取得的資訊驗證，並檢查不同情境

意義：預測未來需要模擬實際使用時的資料可得性。平均誤差、尖峰失誤與跨時段表現各有意義，單一指標不能代表所有用途。

證據：多站點負載研究的結果因站點而異 [6]；可解釋家庭能源估計研究指出異常客群的表現問題 [9]。這支持按情境檢查模型，而非直接沿用他人分數。對本案下一小時任務，依時間順序訓練與測試、只用預測時點前資料，是為符合該任務定義而提出的評估要求，不聲稱所引研究都採同一流程。

如何影響設計：歷史回放固定「截至哪個時間」；特徵、補值與訓練程序避免使用未來觀測。至少與簡單基準比較 MAE、RMSE；必要時另檢查高用電時段。不將單次點預測包裝成保證，也不提供未校準的確定信賴範圍。

#### M5 有用的建議需要使用者情境，建議成效需要行為驗證

意義：建議必須能被理解、符合生活需求並有可採取的行動。回答正確、使用者接受、實際改變行為與節電是不同階段。

證據：提供即時能源資訊的隨機對照實驗（RCT）顯示，資訊可能影響能源使用，但情境與參與條件不可忽略 [2]；學生住宅實驗發現，社會比較資訊與能力提升提示的效果涉及動機、參與度與群體差異 [3]。排程 Agent 研究則指出，金錢目標未涵蓋所有舒適、習慣與偏好 [5]。

如何影響設計：建議說明依據、適用條件與需要使用者確認的內容。本案先評估分析與建議品質；沒有介入後的追蹤或對照資料時，不宣稱已節電。生活偏好不足時先澄清；目前不控制實體家電。

### 三個最重要的專業爭論（以本案範圍選取）

| 要素 | 內容 |
| --- | --- |
| 觀點 A：提供社會比較資訊 | 讓使用者知道自己的用電相對同儕或基準的位置，藉由規範與注意力促進行動。 |
| A 的有力證據 | [3] 的社會比較組相對控制組的用電趨勢有所改善；[2] 亦顯示向住戶呈現能源使用資訊可能產生作用，但該研究不是同儕比較實驗，不能作為社會比較機制有效的直接證明。 |
| 觀點 B：能力提升與具體提示 | 使用者除了知道自己「用得多」，也需要了解可以如何調整。與設備或使用情境相關的具體提示，可能更容易轉化為行動。 |
| B 的有力證據 | [3] 的能力提升提示組相對控制組的用電趨勢有所改善，且高基準用電者的部分分析呈現效果；這些群體分析不能直接推廣到所有家庭。 |
| 目前可支持的共識 | 兩者均有研究支持的應用價值；[3] 沒有證明提示優於比較，也未證明兩者完全等效。介入內容、群體與參與程度都重要。 |
| 尚未解決 | 哪些家庭適合哪種資訊呈現或提示方式？效果如何維持？個人化對話是否比固定提示更有效？現有來源不能直接回答本專案 Agent 的長期成效。 |
| 對本專案的設計影響 | 先採同戶歷史比較與有依據的具體檢查建議。單戶資料不能假造同儕排名；本專案不新增同儕比較功能或行為實驗承諾。 |

#### C2 家庭用電模型選擇，應優先追求預測精度，還是透明且一致的解釋？

| 要素 | 內容 |
| --- | --- |
| 觀點 A：強調預測表現 | 為減少誤判，應比較能捕捉複雜關係的模型，並按任務誤差選擇。 |
| A 的有力證據 | [6] 研究 boosting 集成；[9] 的比較中 RF 有較佳表現。這支持實測比較，不代表複雜模型在所有資料都較好。 |

| B 的有力證據 | [9] 因帳單估計的透明與商業需求選擇自訂決策樹，同時明確承認異常客群限制。其任務是年用電估計，不是本案下一小時預測。 |
| 目前可支持的共識 | 預測準確度與解釋品質應分別評估，不能認定兩者必然衝突，也不能只因說明聽起來合理，就認為它符合模型實際的判斷依據。模型選擇仍須配合使用情境。 |
| 尚未解決 | 本專案的簡單基準與候選模型表現差多少？何種說明對使用者最有幫助？說明是否反映模型實際的判斷依據？模型在尖峰時段與特殊日期的表現如何？ |

### 十個深度理解問題

以下問題以推理、反例與設計選擇檢核領域理解，並附參考回答要點。

#### Q01｜功率與電量 Why Calculation

問題：某設備以 2 kW 運轉半小時，另外半小時關閉。一小時用多少電？若改看小時平均資料，能否還原它何時啟動及瞬間尖峰？

參考回答要點：電量為 2 × 0.5 = 1 kWh，小時平均功率為 1 kW；平均值不能還原啟停細節或瞬間尖峰。分鐘級平均資料也不等於瞬時峰值。需依量測解析度表述結果。[7]；對應 M1、M2。

#### Q02｜負載移時 What-if Trade-off

問題：將一項消耗 2 kWh 的活動移到另一時段，是否必然同時省電、省錢與減碳？要知道哪些資訊才能判斷？

參考回答要點：若活動耗能不變，單純移時不會減少其 2 kWh；費用取決於費率與計費規則，排放取決於適合的時段碳強度資料及估計範圍，尖峰影響也取決於其他同時負載。沒有這些資料便不保證三種效果。[8] 及量測推論；對應 M1、M5。

#### Q03｜缺值 Failure Case Evidence

問題：某小時有一半分鐘紀錄遺失，Agent 能否直接將剩餘紀錄加總，並說成完整一小時用電？若補值，需要揭露什麼？

參考回答要點：不能把部分觀測總量當完整量測；缺值不一定隨機，剩餘平均也不一定代表缺失期間。應交代有效筆數、涵蓋率、補值假設與估計性質；缺失太多時縮限或不給完整總量，門檻需事先定義。補值不得在歷史預測測試中偷用未來資料。[6][7]；對應 M2、M4。

#### Q04｜設備粒度 Real-world Scenario Design Decision

問題：洗衣間設備群的用電量比昨天增加，能否回答「洗衣機耗電增加」？需要什麼額外證據？

參考回答要點：不能直接確定，因為該組量測資料也涵蓋其他電器，例如冰箱與烘衣機。可說明設備群與用電增加的時段，並詢問使用紀錄；要確認單一設備的耗電，通常需獨立量測，或另有經驗證的辨識方法與不確定性說明。本專案目前未納入此類設備辨識方法。[7]；對應 M2、M3。

#### Q05｜異常與浪費 Comparison Failure Case

問題：相較前一天晚間，用電明顯增加，但當天家中有聚會。應把高值刪掉、判定浪費，還是保留？如何選比較基準？

參考回答要點：先分辨量測錯誤與真實事件；真實活動高值應保留並標記情境。比較可考慮同星期／相似時段與活動差異，不能以不相似基準斷言浪費。報告偏離程度與假設，原因仍需補查。[4][6][7]；對應 M3、M5。

#### Q06｜平均誤差與尖峰 Trade-off Comparison

問題：模型 A 的整體 MAE 較低，卻常低估最高用電時段；模型 B 平均誤差稍大但峰值較穩定。哪個適合本專案？

參考回答要點：先依用途判斷；不能只選單一平均數最低者。需保持相同測試期間，比較 MAE、RMSE、峰值時段偏差及穩定性；報告取捨，而非先假設複雜或簡單模型必勝。對話回答正確性仍需另測。[6][9]；對應 M4。

#### Q07｜時間洩漏 Why Design Decision

問題：為什麼預測下一小時時，不宜任意隨機切分所有紀錄，或先用全資料補值後再切分？請舉出偷看未來的例子。

參考回答要點：本專案的測試要模擬時間向前的使用，未來時段不能參與模型訓練與前處理學習。例如，用目標小時的設備群用電量預測同一小時總電量，或用後一天的觀測補上預測時點的缺值，都可能使用當時尚未知的資訊。訓練、調參與測試須依時間分開，並明確界定每項特徵何時可取得。這是配合本專案任務提出的評估設計，不表示所有研究都不能採用隨機切分。對應 M4。

#### Q08｜文字與工具不一致 Evidence Failure Case

問題：工具結果顯示昨日比前日增加 8%，Agent 卻寫「下降 8%」，引用的圖表又來自另一日期。應如何處理與評分？

參考回答要點：視為回答與證據不一致，即使句子流暢也不通過。重新核對日期、分母、增減方向、單位與圖表識別；修正後才能回答，無法釐清則說明。保留工具結果及檢查記錄以重現；數值、時間與證據一致性分項計分。[4][5] 與本案設計推論；對應 M1–M4。

#### Q09｜建議品質與節電 Why Evidence

問題：如果回答正確、建議也合理，是否足以宣稱系統讓家庭節電？還需要什麼研究？

參考回答要點：不足以推論節電；使用者可能未採納，或使用需求、季節、設備改變造成差異。需要介入前後量測、適當對照與情境控制；條件允許時可規劃隨機試驗。參考 [2][3] 的驗證層次，不直接借用其效果。本案先驗證分析與回答品質。對應 M5。

#### Q10｜跨家庭泛化 What-if Real-world Scenario

問題：在法國單一家庭歷史資料上表現良好，能否宣稱適用台灣各類家庭？如果使用者詢問台灣電費或某台冷氣耗電，系統應怎麼回應？

參考回答要點：不能直接推廣；須考慮家庭規模、氣候、設備、時代與計費制度，並增加外部家庭測試。未提供適用費率、帳期／契約資訊或獨立設備紀錄時，先澄清或縮限回答；不套用國外／過時費率，也不猜單機耗電。本案資料只驗證原型流程。[1][5][7][8]；對應 M1、M2、M4、M5。

## Proposed Scheme 系統設計

### System Architecture

系統由單一 LLM Agent 協調分析與知識工具，並設置證據紀錄及回答檢查模組。圖中 ①–⑧ 對應下列表格；工具與知識來源形成證據，供 Agent 整理回答及後續核對。

圖 1 System Architecture

| 模組 | 主要工作 | 輸入 | 輸出與邊界 |
| --- | --- | --- | --- |
| ① 查詢與歷史回放設定 | 接收問題、設定回放基準日期與可用資料截至時間，呈現目前情境 | 使用者問題、回放設定、已確認的對話參數 | 含明確時間基準的需求；「昨天」以回放日期解讀，不冒充目前即時監測 |
| ② 規劃與工具協調 Agent | 辨識任務、釐清需求、選工具、依工具結果調整步驟，整合回答 | 問題、時間基準、工具說明、已取得證據 | 工具呼叫、澄清問題、回答草稿；負責協調，不自行編造工具計算結果 |

### Data 與分析方法

#### 預測時間

以原始紀錄的時鐘時間定義每小時區間[h,h+1)，不自行轉成台灣時間。回放截至時間為小時邊界 h，Agent 只能取得時間戳小於 h 的真實觀測；下一小時目標為區間[h,h+1)的電量，記為 y_h。

例如回放時間為 14:00，最近完成的小時是 13:00–14:00，目標為 14:00–15:00。查詢「昨天」則依回放日期解讀。原始分鐘平均值依所標記的分鐘歸入區間，不推定感測器未記載的傳輸延遲或瞬時峰值。

#### 單位換算

全屋平均用電功率（總有功功率）P_i 以 kW 記錄，每筆代表一分鐘的平均值；完整小時電量為 Σ(P_i/60)，單位為 kWh。

設備群每分鐘的用電量 e_i 以 Wh 記錄；完整小時電量為 Σ(e_i)/1000，單位為 kWh。

日總量為完整日期內的分鐘電量總和；日期是否完整須檢查，不直接把部分起訖日當全天。

所謂「最高用電時段」本案指小時電量最高的區間，不聲稱是瞬間最大功率。

以上換算依 UCI 欄位定義 [7] 推導；全屋功率欄位與設備群電量欄位須分別使用對應公式。

#### 完整性與缺值

依所查欄位分別檢查資料；其他不使用欄位缺值，不自動否決可用欄位。

每小時所需 60 個不同分鐘均有有效數字，才產生該欄位的完整觀測電量。NaN、非數值及未解決的衝突紀錄不能當零。

同時間戳且內容完全一致的重複列可去重並記錄；數值衝突則標為無法確認，不任意挑選。

未完整時段只回報已觀測部分、涵蓋率及限制，不輸出未標明的外推總量；本版不自動補值。

完整日需依原始時鐘格網核對分鐘是否齊全；不完整日期不稱完整全天實測值，也不以不完整基準計算全日增減百分比。

百分比變化以比較基準為分母；分母為零時只報絕對差異，百分比標不適用。

這是保守的初版策略，會犧牲部分可分析資料。後續需報告被排除時段比例；若要加入補值，另定方法及敏感度評估，不在測試後為提高分數臨時改規則。

#### 兩個基準與一個候選模型

| 方法 | 預測 y_h 的方式 |
| --- | --- |
| Persistence | 使用 y_(h-1)，即上一個完整小時。 |
| Daily Seasonal Naive | 使用 y_(h-24)，即前一天相同時段。 |
| Random Forest Regressor | 從預測時點以前的歷史與已知時間特徵學習非線性關係。 |

RF 初始參數建議為 n_estimators=200、max_depth=12、min_samples_leaf=5、random_state=42。這些是可調整的初始設定，尚未驗證為最佳參數。若需調整，只使用訓練與驗證區間，記錄所有選擇，並在最終測試前固定設定。

#### 特徵

過去電量：y_(h-1)、y_(h-2)、y_(h-24)、y_(h-168)。

最近 3 個、24 個完整小時的平均與標準差，計算區間結束於 h，不含目標小時。

已知時間：目標小時、星期幾、月份及週末標記；日型僅是日曆代理，不代表實際家庭作息。

不使用當前資料未提供的氣象、住戶活動、台灣費率或設備開關狀態。

所需特徵時段缺失時，不生成該 RF 預測。若基準資料足夠，可以清楚標示為基準估計，不冒充 RF 輸出。只需要特徵實際使用的時段完整，不要求相隔 168 小時的整段資料全部完整。

#### 切分與評估

先在完整時間格網上，依時間由早到晚定義 70%訓練、15%驗證、15%測試邊界，再按資料完整性建立可用樣本；不先刪除缺值後把不連續列誤當等距時間。訓練標籤只來自訓練區間，最終模型在設定凍結後可合併訓練與驗證資料重訓一次，再測試。

測試採逐小時歷史回放的一步預測：每個時點可使用當時已完成的實際過去小時，包括較早的測試小時，但不使用未來或目標小時。這不是一次預測整段測試期；模型不在測試中反覆調參。

模型檔需記錄訓練資料與標籤的截止時間；其截止不得晚於回放截至時間 h。不能用後期資料訓練的模型回到較早日期預測，否則即使輸入特徵只有過去值，仍可能洩漏未來。正式 Agent 題集的回放時點選在最終測試區間；若之後允許更早回放，必須使用當時可用的模型，或說明沒有符合時間條件的模型。

三方法在共同可用、且目標實際值完整的測試時點比較 MAE、RMSE（kWh），另報各方法可產生預測的比例與樣本數。可附月份／高用電時段分組，但不只挑選好看的月份。未通過資料條件的樣本另報排除原因；不把缺值目標補成標準答案。

#### 參考集合

對目標小時，從它之前 56 天取相同時刻、相同「平日／週末」日型且資料完整的紀錄。至少 14 筆才判定；不足則說明參考資料不足。若一次分析多個目標小時，每個小時均只使用它之前的紀錄作參考。

此集合能部分控制時刻與日型，但無法控制未提供的氣象、假日、住戶活動及季節突變；不可當成真實相同情境。

#### 判定

令 m 為參考集合中位數、MAD 為 median(|x_i-m|)，計算修正分數 M=0.6745×(x-m)/MAD，初值以|M|>3.5 標記候選[12]。

56 天、14 筆與日型分組是本組初始設定；NIST 沒有為本案驗證這些參數。

3.5 為啟發式標記門檻，不是已校準的顯著水準、故障機率或對家庭用電的保證。

MAD 為零或資料不足時，不除以任意小數強行製造高分；只呈現可核對差異，說明無法用本規則穩定判定。

高低值均可標記；原始資料保留，除非另有證據證明是量測錯誤。

#### 如何驗證

本資料沒有真實故障／浪費標籤，不報真實故障辨識 Accuracy 或 F1。先檢查公式、時間隔離及邊界處理，再以案例圖表檢視標記與參考是否合理。可在驗證區間比較 2.5／3.5／4.5 的標記頻率以說明敏感度；這不是以無標籤資料宣稱找到了正確門檻。

若後續透過修改資料來模擬異常，只能驗證系統是否能辨識這些人為設定的情況，不能直接代表它能偵測真實家庭中的異常用電。

### Domain Knowledge 與回答檢查

#### 約 10 條有來源的知識條目

初步涵蓋：功率與電量、設備群資料的判讀限制、缺值、比較基準、零分母、異常候選、預測限制、節電／省費／削峰的差異、建議與行為成效，以及跨家庭適用限制。每條知識均包含定義、適用條件、不能推論的事項與來源編號。

先透過概念標籤與關鍵詞取得少量候選知識條目，再由 Agent 選擇相關內容；沒有相符內容時，不假造檢索結果。初版先使用小型知識集合，是否需要向量資料庫留待後續評估；取得相關知識後，仍須核對其是否適用於當前問題。

#### 結構化回答

回答草稿分為：使用者問題的時間解讀、數值結果、可引用證據 ID、觀察／預測／假設分類、建議與限制。前台文字與圖表由同一結果 ID 產生或核對。紀錄工具輸入輸出，不要求保存模型內部思考過程。

比對數值時，允許四捨五入及電腦浮點運算造成的微小誤差。例如，保留兩位小數時，四捨五入的容許差距為 0.005，另保留浮點運算所需的極小容差。增減方向、百分比分母、時間範圍與單位須分別檢查，不能僅因數值接近就忽略日期錯誤。

系統預計自動核對回答中的日期、數值、單位與引用，並檢查是否違反明確限制，例如在缺乏個別電器資料時，直接斷定某台電器造成用電增加。其他較難用固定規則判斷的推論與建議，則由人工評分確認是否有足夠依據。

#### 工具及修正上限

每個任務最多 8 次 Agent 發起的工具呼叫，失敗呼叫也計入；工具內部的一致性檢查不額外算 Agent 呼叫。回答檢查後最多再產生 1 次修正版，且所有後續工具仍受同一 8 次上限限制。再次失敗時回傳可確認部分或限制說明，記錄未完成原因。

數值規則檢查本身不必再次呼叫 LLM；修正需要的額外模型回合及工具成本須在評估中記錄。

### Pseudocode

#### Algorithm 1 Energy Detective Agent

Input: User query Q; fixed replay time h; read-only data view V

Output: Evidence-linked response R

```text
01: C <- FreezeContext(h, V, data_version, model_version, knowledge_version)
02: E <- empty evidence registry; calls <- 0; repairs <- 0; issues <- empty
03: while true do
04:     A <- PlanNextAction(Q, C, E, issues) or SERVICE_ERROR
05:     if A.type = CLARIFY then
06:         return RenderClarification(A.required_fields, C)
07:     end if
08:     if A.type = TOOL then
09:         if calls >= 8 then
10:             return SafeTerminal(E, C, reason = TOOL_BUDGET)
11:         end if
12:         calls <- calls + 1
13:         T <- ExecuteGuardedTool(A.name, A.arguments, C) or FAILURE
14:         E <- Record(E, T, tool = A.name, arguments = A.arguments, context = C)
15:         continue
16:     end if
17:     if A.type != DRAFT then
18:         return SafeTerminal(E, C, reason = INVALID_ACTION_OR_SERVICE_ERROR)
19:     end if
20:     D <- BindDraftToEvidence(A.draft, E, C)
21:     report <- ValidateResponse(D, E, C)
22:     if report.pass then
23:         return RenderResponse(D, E, C, status = ANSWER_OR_PARTIAL)
24:     end if
25:     if repairs >= 1 then
26:         return SafeTerminal(E, C, reason = VALIDATION_FAILED)
27:     end if
28:     repairs <- repairs + 1
29:     issues <- report.issues; Q <- AddRepairInstruction(Q, issues)
30: end while
```

輔助程序的必要行為：

ExecuteGuardedTool 檢查名稱與參數、固定時間／視圖、欄位完整性及各工具前提；錯誤回傳結構化失敗原因。無效嘗試也計入 calls，原始資料不被修改。

PlanNextAction 每次僅回傳 CLARIFY、TOOL、DRAFT 或錯誤；不能以空動作持續迴圈。每個繼續路徑都消耗一次工具呼叫或一次修正，因此不需要等待未知條件才終止。

BindDraftToEvidence 只接受草稿明確指定且存在的證據 ID，附上核對資訊；不為缺乏依據的文字自動找一筆看似相關的引用來補上。

ValidateResponse 檢查必要欄位、時間、單位、數字、方向、圖表 ID 及明確限制。無法由規則涵蓋的自由文字推論，仍由後續人工評估。

SafeTerminal 用固定結構呈現已可確認的事實或限制理由，不把未通過檢查的草稿直接輸出，不進行第二次生成式修正。可引用證據不足時只說明原因。

回答修正後若 Agent 需要工具，仍使用同一 calls 計數；達到 8 次後也可用現有證據修正文句，但不能取得第 9 次工具結果。

#### Algorithm 2 完整性檢查與電量統計

Input: Historical records D; field F; interval I; fixed context C

Output: Observed energy, completeness and evidence metadata

```text
01: if I is invalid, empty or ends after C.h then return LIMITED(INVALID_INTERVAL)
02: D <- RestrictToViewAndTime(D, C.V, timestamps < C.h, interval = I)
03: D <- DeduplicateIdenticalRecords(D); mark conflicting timestamps invalid
04: G <- ExpectedMinuteGrid(I, original_recorded_clock)
05: valid <- FiniteNonconflictingValues(D, field = F, expected_grid = G)
06: if Count(valid) = 0 then return LIMITED(NO_VALID_OBSERVATIONS)
07: coverage <- Count(valid) / Count(G)
08: if F is Global_active_power then
09:     observed_kWh <- Sum(valid.values / 60)
10: else if F is Sub_metering_1, Sub_metering_2 or Sub_metering_3 then
11:     observed_kWh <- Sum(valid.values) / 1000
12: else
13:     return LIMITED(reason = FIELD_NOT_SUPPORTED_FOR_ENERGY_SUM)
14: end if
15: complete <- AllExpectedMinutesHaveOneValidValue(G, valid)
16: label <- COMPLETE_OBSERVED if complete else PARTIAL_OBSERVED
17: return Result(observed_kWh, coverage, complete, label, unit = kWh, C)
```

若區間在 h 之後或完全沒有可用紀錄，工具回傳限制狀態；不能因空加總得到 0 就回答「沒有用電」。詢問「今天」時需先確定是截至 h 的已發生部分，還是整日；若縮小查詢區間，回答也須顯示縮小後的範圍。完整小時需要 60 個不同分鐘。完整日須檢查整個原始日期格網；日期中有缺失則不是完整日。若用電工具內部處理的是不完整區間，只能產生 PARTIAL_OBSERVED，不可拿來當完整日百分比的分母。

#### Algorithm 3 下一小時預測

Input: Fixed replay boundary h; visible hourly history H; model artifact M

Output: Labeled estimates for interval[h,h+1), or limitations

```text
01: H <- VisibleCompleteHoursBefore(h)
02: estimates <- empty; limitations <- empty
03: if y_(h-1) is available then add PERSISTENCE(y_(h-1)) to estimates
04: if y_(h-24) is available then add DAILY_NAIVE(y_(h-24)) to estimates
05: if M is unavailable or M.training_cutoff > h then
06:     return LabeledEstimatesOrLimit(estimates, reason = MODEL_UNAVAILABLE_AT_TIME)
07: end if
08: X <- BuildPastOnlyFeatures(H, lags = [1,2,24,168], windows = [3,24])
09: X <- AddKnownCalendarFeatures(X, target_hour = h)
10: if any required historical value is missing then
11:     return LabeledEstimatesOrLimit(estimates, reason = FEATURES_INCOMPLETE)
12: end if
13: prediction <- M.predict(X) or FAILURE
14: RecordPredictionOrFailure(estimates, limitations, prediction, M.version)
15: return Result(estimates, limitations, target = [h,h+1), cutoff = h, unit = kWh)
```

不在此程序重新訓練模型。實際目標值 y_h 只供事後評估取得，不進入 Agent 可見視圖。無 RF 時可呈現已標示名稱的基準，不把它稱成 RF 預測。此設計不產生未校準的預測區間。

#### Algorithm 4 異常候選標記

Input: Complete observed energy x at hour s; visible historical hours H

Output: Candidate flag and reference evidence, or limitations

```text
01: if hour s is incomplete or not fully visible then return LIMITED(INCOMPLETE_TARGET)
02: B <- CompleteHours(H, start >= s-56 days, end <= s)
03: B <- SameHourOfDayAndWeekdayWeekendType(B, s)
04: if Count(B) < 14 then return LIMITED(INSUFFICIENT_REFERENCE)
05: m <- Median(B.energy)
06: mad <- Median(Abs(B.energy - m))
07: if mad = 0 then
08:     return DifferencesOnly(x, m, reason = ZERO_MAD)
09: end if
10: score <- 0.6745 * (x - m) / mad
11: candidate <- Abs(score) > 3.5
12: return Result(candidate, score, median = m, MAD = mad, count = Count(B),
13:               label = ANOMALY_CANDIDATE, no_confirmed_cause = true)
```

參考小時必須結束於 s 以前；如小時起點為 s，end<=s 表示不含目標小時。此處未做統計顯著性檢定，沒有真實故障或浪費標籤。MAD 為零時只報差異，不強行加入任意小數分母。

### 失敗情況處理

| 情況 | 預期行為 |
| --- | --- |
| 日期模糊 | 澄清日期，不自行使用系統今天代替歷史回放日。 |
| 資料缺失 | 顯示已觀測部分及涵蓋率，不偽裝完整量測。 |
| 百分比基準為零 | 報絕對差，百分比不適用。 |
| 詢問洗衣機／冷氣單機原因 | 說明資料僅能呈現設備群的用電情況，提出有條件的檢查方向或進一步詢問。 |
| 參考樣本不足／MAD=0 | 限制異常判定，只報可確認差異。 |
| 模型訓練截止晚於 h | 不使用該 RF；有基準時清楚標示，否則說明不足。 |
| 工具逾時或失敗 | 記錄失敗原因，不編造成功結果；後續仍受 8 次上限。 |
| 回答與證據不符 | 最多修正 1 次；仍不通過則提供可確認部分或限制。 |
| LLM 服務尚未設定或中斷 | 回覆服務限制，記錄未完成原因，不編造工具結果。 |

## Evaluation Plan 評估計畫

### 題集

獨立試測 10 題：與正式題目分開，用於調整工具說明與題目格式，不列入正式評估結果。

正式 50 題：五類任務各 10 題；每類 6 題一般情境、4 題資料不足或邊界情境，共 30 題一般、20 題邊界。

正式題的回放截至時間選在最終測試區間，並遵守模型訓練截止限制；歷史比較可查更早紀錄，但不得因此讓模型學到未來標籤。

每題固定回放時點、資料視圖、標準答案或應澄清／說明限制的行為，以及評分規則。

遮蔽資料或模擬工具失敗只發生在測試視圖，不改原始檔；預期答案必須以該視圖實際可用資料為準。

正式題集在測試前凍結；不因模型答錯而重新解釋答案。題目由組員複核，不能全部依賴同一 LLM 產生及評分。

### 兩個條件

| 條件 | 固定內容 | 差異 |
| --- | --- | --- |
| A：無外部回答檢查 | 同一 LLM 版本、工具、知識、資料、任務、回答格式與初始提示 | 生成回答後，直接交由離線評估；不啟用 ⑦ 的外部檢查與修正。 |
| B：有外部回答檢查 | 與 A 相同 | 啟用⑦、至多 1 次修正及限制回覆；受相同工具上限。 |

兩者均可自行澄清，均保留⑥證據紀錄供評估，不把「沒有檢查」誤作「沒有工具或知識」。比較的是整個檢查／修正方案的效果，不能把增加推理回合的影響全部歸因於某一條規則；同步報告時間與成本。

每條件每題執行 3 次，共 50×2×3=300 次任務執行，另有獨立試測。一次任務可包含多次模型回合，因此不是 300 次 API 呼叫，也不是目前已執行 300 次。LLM 供應商、固定模型 ID 與可用生成參數待選定；未取得模型服務前不聲稱已完成實驗。

### 指標與避免偏誤

| 面向 | 定義／計畫 |
| --- | --- |
| 任務完成率 | 按各題凍結標準評分；一般題須給必要結果，邊界題須做正確的澄清或限制處理。 |
| 數字／單位／時間正確性 | 對一般可回答題，依預期必要欄位計分；缺少必要欄位即算失敗，避免只評估已輸出的數值。 |
| 證據一致性 | 檢查回答中可核對的主張是否與實際證據一致，同時報告回答涵蓋情況與任務完成率，避免透過減少回答內容或拒答取得表面高分。 |
| 適當限制處理 | 對 20 題邊界情境報告正確澄清／限制率；對 30 題一般情境另報不必要拒答率。 |
| 建議品質 | 兩位組員獨立評分相關題：證據支持、推論界線、可採取性，各 0–2 分；報初始一致情況並記錄分歧處理。合理性不以 LLM 自評為唯一依據。 |
| 執行成本 | 每題時間、Agent 工具呼叫次數、修正次數、模型用量與可取得的費用紀錄。 |
| 穩定性 | 報告各次執行及各題結果，不只挑最佳一次；相同題目重複結果不當成彼此獨立的不同問題。 |

沒有預設必須提升幾個百分點的結論。若 B 無改善、較慢或拒答較多，也應如實報告並分析。

### 預測與異常分析的驗證

預測測試使用共同可比較時點的 MAE、RMSE 與各方法覆蓋率。異常資料沒有真實故障或浪費標籤，因此檢查計算與邊界處理、案例合理性及門檻敏感度，不將候選標記率稱為故障辨識準確率。評分端的事後真值與人工答案不回傳給正式測試中的 Agent。

## Expected Outcomes 預期成果與限制

預期完成具有明確工具輸入輸出規範的家庭用電 Agent 設計、可追溯的回答證據與可重現的評估紀錄。研究將比較外部檢查帶來的回答品質、耗時與額外模型用量，不預設一定改善。現階段尚無實驗結果。

本專案受單一家庭、較早期的歷史資料、設備群量測粒度，以及缺乏真實異常標籤等條件限制。固定規則無法保證所有文字推論均有足夠依據，建議合理性仍需人工複核。缺乏使用者採納紀錄及實施建議後的量測時，不宣稱已達成節電、省費或減碳。
